# Vault device authorization

Status: implemented in the base reader/creator dashboard. This is an additive
companion to `banksia.vault@1`; no new signing key or payment is required.

## Problem

A reader key is a P-256 key held by one browser origin on one device. The grant
bulletin wraps the period ring key to that key's thumbprint. Logging into the
same Hive account on a phone therefore does **not** give the phone the private
key, and copying the private key between devices is awkward and makes the key
long-lived in two places.

Device authorization lets a signed-in reader add a second device without moving
the private key, paying again, or typing a recovery passphrase.

## Flow

1. The reader opens a premium post on the new device and is signed in as the
   same Hive account that pays for the membership.
2. The device generates its own P-256 reader key locally.
3. The device writes only the **public key** to the reader's account metadata:
   `posting_json_metadata["banksia.io"].reader.devices["<creator>"][...]`.
   The write is one `account_update2` signed with the reader's **posting** key.
4. The creator dashboard already derives active subscribers from its payment
   history. It fetches those subscriber accounts in bulk with `get_accounts`,
   reads the registered device keys, and wraps the ring key to each key.
5. The new device polls the bulletin, finds its own entry, unwraps the ring key
   and unlocks locally. No payment or key transfer occurs.

The paywall exposes this as **Use my membership on this device**.
`/subscriptions` exposes the same action once per active plan when the current
device has no reader key for that creator.

## On-chain shape

```json
{
  "banksia.io": {
    "reader": {
      "v": 1,
      "devices": {
        "ausbit.vsc": ["p256:base64url-uncompressed-point"]
      }
    }
  }
}
```

- Only public keys are present. There is no token, secret or entitlement in the
  metadata.
- The creator is identified by the map key. A reader can authorize devices for
  several creators independently.
- Keys are deduplicated and capped at `VAULT_DEVICE_MAX_KEYS` (8) per creator.
- The writer merges into the latest account metadata, preserving `profile`,
  `banksia.io.blog` and every unknown field.
- A missing key is a revoke request: the creator stops wrapping it on the next
  bulletin. Existing grants remain valid until their signed expiry, matching the
  protocol's normal revocation model. `/subscriptions` offers **Remove account
  key** for a key held on the current device (and **Forget this device key** to
  delete the local copy). A key on a lost device has to be removed by updating
  the account metadata from another signed-in device.

## Why account metadata instead of `custom_json`

The reserved `custom_json` registry (`banksia.vault.reader_key`) is the cheapest
write per device, but there is no global `custom_json` index in the public
Condenser API. The creator would have to scan every subscriber's history, which
is O(subscribers × history pages) per refresh. The account metadata directory is
read in bulk with `get_accounts` (up to 1,000 names per request), so discovery is
O(subscribers / 1,000) RPCs.

Trade-off: `account_update2` rewrites the whole `posting_json_metadata`, which
is heavier than a small `custom_json`. Device authorization is rare, so one
heavier posting operation per device is a reasonable price for scalable
discovery without a relay or HAF index. The `custom_json` schema remains
reserved for a future indexer/relay path and for other frontends that run their
own index.

Concurrent writes to account metadata can overwrite each other. The app fetches
the latest account before building the operation; a simultaneous profile edit
from another app is a known race. Re-running the device action is safe and
idempotent.

## Creator-side discovery

`src/pages/blogVault.vue`:

- `attachDeviceKeys()` reads the payments' subscriber accounts, calls
  `fetchAccounts(..., { force: true })`, which batches `get_accounts` calls,
  parses `readReaderDevices()`, and attaches all keys to each subscriber row.
- `refreshDeviceKeys()` repeats the account read on the auto-issue tick (at most
  once a minute), so a phone that authorizes itself does not wait for a full
  dashboard reload.
- `issueGrants()` wraps every active subscriber key, plus explicitly selected
  rows. The bulletin is cumulative: it must always include all active entries or
  older members would disappear from the newest manifest.
- The subscriber table shows the primary payment key and `+N devices`; the grant
  pill is aggregated across every key.

## Reader-side state

- `device-pending`: `Waiting for the creator to grant this device.` The normal
  two-minute visibility-aware poll and the explicit **Check again** action still
  apply.
- The device key is generated by `ensureReaderKey(blog, { account })`, so two
  accounts on one browser remain separate subscribers.
- Recovery export/import remains the fallback for devices that cannot sign a
  posting operation, anonymous readers or a creator who is offline.

## Chain-cost audit

The audit looked at every Vault write path.

| Write | Current behaviour | Notes |
| --- | --- | --- |
| Subscription payment | One `recurrent_transfer` or `transfer` with a compact HOM + `banksia` memo | Keep. The memo is the only source of truth for money. |
| Device authorization | One `account_update2` per device | Posting key, no payment, bulk-readable by the creator. |
| Bulletin (small) | One compact v1 `comment` up to 300 entries | Keeps small blogs to one comment. |
| Bulletin (large) | One v2 manifest + one comment for each changed shard | Unchanged shards keep their revision, hash and permlink. |
| Bulletin entry | Compact v1 object or v2 tuple | v2 uses `[rkt8, epk, iv, ct, expiresEpoch]`; default `alg`/`tier` are omitted. |
| Manifest overhead | Keyring, shard descriptors `[index, rev, hash]` | Empty `claims`, `delegation: null` and `keyring.alg` are omitted. |
| Blog vault pointer | One small `account_update2` when the pointer changes | Fine; only on issuance. |

The structural cost is now bounded:

- A v2 reader fetches only the manifest and its own shard.
- A new reader publishes one changed shard and the manifest; unchanged shards
  keep their existing comments.
- Shard count grows with reader count, from 8 to 1,024, targeting about 200
  entries per shard.
- The dashboard fetches shards with bounded concurrency and can merge all of
  them for grant status.
- Grant batching is configurable at 30, 60 or 120 seconds. Longer windows reduce
  manifest and shard writes during registration bursts.

Remaining limits, not blockers for a large launch:

1. **Manifest size.** At 1,024 shards the descriptor list is roughly 50 KB,
   still within the 60 KB comment budget. A creator beyond roughly 250,000
   active reader keys would need a two-level manifest.
2. **v1 compatibility.** A v1 reader rejects a v2 manifest and stays locked.
   Deploy the v2 reader before a large creator crosses the 300-entry threshold.
3. **Relay/HAF indexer.** Still optional. A relay can issue while the creator is
   offline; it is not required for sharded read/write scalability.
4. **Device count.** Each registered device is one reader entry. The eight-device
   cap and recovery fallback keep that growth bounded.

Bloom filters were intentionally not added: the v2 shard index is exact
(`firstRktByte % shardCount`), so a Bloom filter would add manifest bytes without
saving a fetch.
